CATEGORY 1: MACHINE LEARNING & ALGORITHMIC RIGOR

Q1: Why did you choose K-Means over DBSCAN or Hierarchical Clustering?
Answer:
- Scalability: K-Means runs in O(N * K * d * i) time, making it exceptionally fast and scalable
  for hundreds of thousands of retail transactions.
- Actionable Centroids: K-Means produces definite cluster centroids (median R, F, M), which give
  store owners explainable reference points directly linkable to marketing strategies.
- Why not DBSCAN? DBSCAN flags low-density points as noise (cluster -1). In retail CRM, every
  single customer must be assigned a marketing cohort; dropping inactive or VIP spenders as "noise"
  is unacceptable. Additionally, retail spend densities vary wildly, making a single epsilon (eps)
  parameter impractical.
- Why not Hierarchical? Agglomerative clustering requires O(N^2) memory and O(N^3) time, which fails
  on production datasets.

Q2: Why did you apply log-transformation and Z-score standardization before clustering?
Answer:
- Retail transactional spend exhibits extreme positive skewness (Power Law/Pareto distribution),
  where 80% of purchases are small and a few VIPs spend massive sums.
- Because K-Means computes Euclidean distance: sqrt(sum(x_i - y_i)^2), a monetary difference in
  thousands of rupees would completely overwhelm 1-digit frequency differences.
- We compress the heavy monetary tail using x' = ln(x + 1), then standardize all 3 features to zero
  mean and unit variance using Z-score scaling: z = (x' - mu) / sigma.

Q3: How did you select the optimal number of clusters (K)?
Answer:
We implemented an automated programmatic evaluation loop sweeping K from 2 to 6, measuring:
1. Silhouette Coefficient (Rousseeuw, 1987): Measures cohesion vs. separation. Our peak was at
   K=3 (score: 0.4562).
2. Davies-Bouldin Index: Evaluates average similarity between each cluster and its most similar one.
   Lower is better (0.7150 at K=3).
3. Calinski-Harabasz Index (Variance Ratio): Measures ratio of between-cluster to within-cluster dispersion.

Q4: What does a Silhouette Score of ~0.45 mean? Is it good enough?
Answer:
Yes, absolutely. In synthetic benchmark datasets (like Gaussian blobs), scores can exceed 0.70.
However, in real human consumer behavior, spend patterns are continuous rather than strictly isolated.
Published academic literature (e.g., Chen et al., 2012) confirms that real retail RFM clustering
consistently yields Silhouette scores between 0.35 and 0.45. A score of 0.4562 indicates dense,
well-separated behavioral cohorts without artificial overfitting.

CATEGORY 2: ARCHITECTURE & SYSTEM DESIGN

Q5: Explain your backend architecture and separation of concerns.
Answer:
Our FastAPI backend adheres to clean layered architecture:
- Routers (`backend/routers/`): Handle HTTP request routing, status codes, and JSON serialization.
- Services (`backend/services/`): Pure business logic completely decoupled from HTTP (`ingestion.py`,
  `rfm.py`, `clustering.py`, `fatigue.py`, `recommendations.py`).
- Schemas (`backend/schemas/`): Pydantic v2 DTOs guaranteeing strict data validation and type safety.
- Models (`backend/models/`): SQLAlchemy 2.0 ORM entities for database tables.
- Adapters (`backend/adapters/`): Abstract interface (`WhatsAppAdapter`) implemented by
  `MockWhatsAppAdapter` (for safe zero-cost local evaluation) and `LiveWhatsAppAdapter` (for Meta Cloud API).

Q6: Why did you implement an Adapter pattern for WhatsApp?
Answer:
To ensure safe, cost-free development and compliance with Meta's terms of service:
1. Meta WhatsApp Cloud API charges per template conversation and requires verified business IDs.
2. The `MockWhatsAppAdapter` mirrors Meta's JSON payload responses, masks phone numbers (***3210),
   and tags all messages with a visible [SIMULATED ADAPTER] badge.
3. Swapping to the live Meta API only requires toggling WHATSAPP_LIVE_MODE=true in `.env` without
   altering any clustering or recommendation code.

CATEGORY 3: PRIVACY, ETHICS & MARKETING FATIGUE

Q7: What is Marketing Fatigue, and how does your system enforce guardrails?
Answer:
Marketing fatigue occurs when customers are bombarded with repetitive, irrelevant promotional
messages, leading to high opt-outs, complaints, and brand damage.
Our deterministic Fatigue Engine enforces 3 mandatory rules:
1. Consent Verification: Checks if explicit opt-in consent exists (consent_given == True).
2. Global Suppression Matching: Checks if the user is in an opt-out/DND registry.
3. Rolling 30-Day Frequency Capping: Restricts promotional messages to a maximum of 3 messages
   within any rolling 30-day window. If count >= 3, dispatch is immediately blocked.

Q8: How did you test your project against edge cases?
Answer:
We wrote an automated Pytest test suite with 87 unit tests covering:
- Ingestion of malformed CSVs (missing customer IDs, negative prices, invalid dates, duplicate lines).
- Hand-calculated RFM verification comparing manual math against algorithmic output.
- Fatigue checks ensuring blocked users can never receive a message.
- Small datasets (e.g., N < K) edge case handling.
All 87 tests passed with 100% pass rate in 2.38 seconds.
